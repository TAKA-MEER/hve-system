### 2.1.1 UnitV2 の実機調査の結果（`WP-MEAS-06`。2026-10-06）

PC から USB の有線（`10.254.239.1`）と SSH で調べた（2026-10-06・07）。**機器に残る変更はしていない**（組み込みのサービスは一度止めて、元どおり起動し直した）。

| 項目 | 結果 | 設計への影響 |
| --- | --- | --- |
| OS・Python | Linux 4.9.84（armv7l）・glibc・BusyBox。**Python 3.8.6** | `DD-7` のとおり |
| 入っている依存 | **`aiohttp` 3.6.2・`pyserial` 3.4・OpenCV 3.4.9・numpy 1.16.4・PyYAML 5.3.1**（`zeroconf`・`tomli` は無い） | **OS のものをそのまま使う**。ホストの `.venv38` も同じ版に揃える（[-names.md](DetailedDesign-names.md) §1） |

| **自前の AP** | **同時に `hostapd` が AP `M5UV2_4afd` を `wlan1` で出している**（`th-rpi-ap` と同じ 1 ch・20 MHz） | `th-rpi-ap` の帯域を食いうる（spec `H-A8`）。**配備で止める**（`P-11`。2026-10-07 採用） |
| `.local` の名前解決 | Python（glibc）からは `.local` を引けない（nss-mdns が無い）。`avahi-daemon` と `avahi-resolve-host-name` はあるが、**`/etc/avahi/avahi-daemon.conf` の `allow-interfaces=eth0, wlan1` で `wlan0`（`th-rpi-ap`）を見ていない** | `zeroconf` をやめ、**avahi の `allow-interfaces` に `wlan0` を足し、アプリは `avahi-resolve-host-name -4` で引く**（[DetailedDesign.md](DetailedDesign.md) §4.6・`P-12`。2026-10-07 採用） |
| **カメラの解像度** | **1920×1080 は取れない**（要求すると 1280×720 になる）。取れたのは 640×480（約 15 fps）・**1280×720（約 20 fps）**・**1600×1200（約 4.7 fps）** | spec `H-V9`（1080p の前提）は取り下げ、**720p から切り出すことに決めた**（spec `H-V10`。2026-10-07） |
| 映像の負荷 | 1 スレッドで 取り込み → 中央の切り出し → 480p へ縮小 → JPEG（品質 60）: **1280×720 で 約 5〜13 fps**（縮小の方式による。取り込みの 1 枚に約 46 ms、処理に 33〜85 ms）。1600×1200 で 約 3.6〜5 fps。**そのあいだ CPU 1 コアが 100 %**。メモリは最大 74 MB・空き 75 MB。温度 72〜74 ℃ | OpenCV で YUYV を受けた場合の値。**v2 は MJPEG を受ける方式にした**（下の行・[DetailedDesign.md](DetailedDesign.md) §4.4） |
| **カメラの出力形式**（2026-10-07） | `v4l2-ctl --list-formats-ext`: **MJPEG は 1280×720（30 fps まで）・800×600・640×480・352×288**。YUYV は これに 1600×1200 を足したもの。**1600×1200 は YUYV だけ**（約 4.7 fps しか出ないのはこのため）。JPEG の品質を変える制御は無い | 720p の MJPEG を受けて 480p に作り直す（spec `H-V10`）。そのまま送る方式は予備の手段（spec `H-V11`） |
| **MJPEG をそのまま取り出す**（2026-10-07） | OpenCV 3.4.9 からは MJPEG を選べない（`CAP_PROP_FOURCC` が効かない）。外部のプログラムの出力を Python で 1 枚ずつに区切ると、1280×720 で **29.9 fps（CPU は 2 コアのうち 約 0.2 コア）**。**`ffmpeg` は使えない**: v4l2 のバッファをカーネルに大量に取り（4.2 は 256 個を要求する）、cv2 を読み込んだプロセスと並ぶと OOM になる（実際に温度監視と `haveged` が殺された）。**`v4l2-ctl --stream-mmap=4 --stream-to=-` なら起きない**（標準出力の頭に文字が混ざるので `FFD8` から切る）。1 枚 約 157 KB で一定 → **30 fps で 38 Mbps・15 fps で 19 Mbps・10 fps で 12.6 Mbps** | CPU は空くが、無線の量が 480p（下の行）の約 6 倍になる（spec `H-A8`）。ズームは UnitV2 では行えず、画面側の拡大になる |
| **MJPEG を受けて作り直す**（2026-10-07） | 1 枚あたり: 720p の展開 50 ms（1/2 に縮めながらの展開も同じ）・切り出し＋480p へ縮小 20 ms（線形。面積平均だと 52 ms）・JPEG 化（品質 60）32 ms → **1 コアで約 10 fps**。480p の 1 枚は品質 60 で 26 KB・80 で 41 KB（10 fps で 2.1〜3.3 Mbps） | 処理を 2 スレッドに分ければもう少し出る見込み（未測定。OpenCV の関数は GIL を外す） |
| **連続運転の温度**（2026-10-07） | ②を 15 分続けた（`v4l2-ctl` で 30 fps 取り込み、別スレッドで区切り、主スレッドで展開→480p→JPEG 品質 60）。**72 ℃ から上がって 4 分で 79 ℃ に達し、そのまま頭打ち**。周波数は 1.4 GHz（`performance`）のまま、**fps は 7.0〜7.4 で落ちなかった**。室温・ケース無しで、風は当てていない | 温度監視が動き出す 95 ℃ まで余裕がある。夏場・ケースに入れた状態は `WP-MEAS-05` で見る。30 fps を区切るだけで 1 コアの一部を使うので、取り込みは要る fps まで下げる |
| 温度監視の動き | `check_thermal.py` は 95 ℃ 以上で省電力に切り替え、組み込みのサービスを殺し、**自分で :80 に Flask を立てようとする**（自前のアプリが :80 を持っていれば失敗して例外を出すだけ） | 自前のアプリは温度監視に止められないが、95 ℃ を超えると遅くなる |
| メモリ | 全体 116 MB。**`/tmp` は RAM 上（57 MB）**。OOM になると、カーネルは温度監視など関係の無いプロセスも殺す | 映像を `/tmp` に溜めない。アプリは自分のメモリを抑え、取り込みのバッファも少なくする |
| 温度 | `check_thermal.py` が 95 ℃ 以上で CPU を省電力にし、組み込みのサービスを止める（自前のアプリは止めない） | 長時間の負荷は `WP-MEAS-02`・`05` で見る |
| 書ける場所 | ルート 117 MB 空き（UBIFS）・SD カード `/media/sdcard`（14.5 GB 空き。カードが挿さっていれば） | アプリはルートに置ける大きさ |
| **Grove の UART の電圧とピンの並び**（2026-10-07） | **黄＝UnitV2 の TX**（`/dev/ttyS1` の送信が黄に出る）。**白＝RX**（黄と白を直結した折り返しで 115200・9600 とも 500 バイト一致）。Grove の Vcc はテスタで 5 V だが、**黄（TX）の待機中の電圧は 3.3 V**（UNO から外して測った。ユーザー測定） | **信号は素の 3.3 V（レベル変換は無い）。UNO → UnitV2 には分圧（§2.3）が要る**。Vcc の 5 V を信号の電圧と取り違えない。なお最初の配線は黄→D1・白→D0 の逆で、UnitV2 の TX と UNO の TX がぶつかり、白には D0 の 1 kΩ 越しに 5 V がかかっていた（TX はその後も正常） |
| **UnitV2 → UNO**（2026-10-07） | **黄 → D0（ハードウェアの `Serial`）で、115200 の行を 4000 行（うち 2000 行は間を空けずに連続）すべて正しく受けた**（USB をつないだ状態）。D0 の電圧を A0 で測ると、待機 3.44 V・LOW 0.48 V（16U2 の 1 kΩ と引き合っても UnitV2 の TX が十分に引き下げる）。初めの試験で D0 が 0 バイトだったのは配線の誤り（その頃は線の逆・抜けが続いていた）と見られる。D2 の SoftwareSerial では 38400 で全部届き、115200 では 9 割の行が化けた | **§2.2・§2.3 のとおり D0/D1 で決まり**。SoftwareSerial は使わない。**D0 に線が付いていると USB から書き込めない**（§2.2 の「書き込み中は外す」のとおり。avrdude が `not in sync` になる） |
| **UNO → UnitV2**（2026-10-07） | **D1 → 1 kΩ → 白（→ 2 kΩ → GND）の分圧で、115200・5 ms ごとの行を 20 秒で 3996 行、取りこぼし・化けとも 0**。I2C 用のレベル変換モジュール（端子 `VccA`/`VccB`/`SDAA`/`SDAB`。型番は未確認）は、A・B のどちらを 5 V にしても D1 を押さえて UNO の送信（書き込みを含む）を止めた | **分圧で決まり**（§2.3 のとおり）。I2C 用のレベル変換モジュールは使わない |
| **双方向**（2026-10-07） | 最終の配線（黄 → D0・D1 → 分圧 → 白）・115200 で、UnitV2 が `M` を 10 ms ごとに 2000 行送り、UNO は受けるたびに応答を返しつつ 66 ms ごとに `C` 行を出した。**応答 2000/2000・`C` 629 行の連番の抜け 0・UNO 側の読めない行 0。往復 中央値 2.3 ms・最大 4.2 ms**（UnitV2 の Python で測定） | `IO_BAUD` は 115200 で足りる |

### 2.2 Arduino UNO のピン

| 用途 | ピン | 状態 | 備考 |
| --- | --- | --- | --- |
| UnitV2 との UART | D0（RX）・D1（TX） | 実機で確認（2026-10-07。§2.1.1） | ハードウェアの `Serial`。**書き込み中は UnitV2 との線を外す**（USB と共用のため）。デバッグの出力に `Serial` を使わない（UnitV2 へ流れる） |
| ULN2003 IN1〜IN4 | D4・D5・D6・D7 | **仮** | 半ステップの並びは旧版の実機確認どおり（隣り合うコイルを順に。[-names.md](DetailedDesign-names.md) §5） |
| MG996R の信号 | D9 | 実機で確認（2026-10-07） | **Timer1 のハードウェア PWM（OC1A・50 Hz）で直接出す。`Servo` ライブラリは使わない**: `Servo` は Timer1 の割り込みでパルスを作るので、Timer2 の刻みの割り込み（100 µs ごと）に遅らされてパルス幅が揺れ、サーボが止まっている間も鳴った（実機。割り込みを止めると鳴り止んだ）。D10 の PWM は使えなくなるが使わない |
| SRF02 SDA / SCL | A4 / A5 | UNO の I2C | **5 V の I2C なので直結**（レベル変換不要）。アドレスは**この個体は 0x72**（7 bit。工場出荷は 0x70。旧版の実機でも 0x72 だった。2026-10-07 に UNO の I2C の一覧で確認） |
| ステッピングの刻み | Timer2 | — | サーボの PWM が Timer1、`millis` が Timer0 を使うため |

### 2.4 Arduino の決まりごと

| 部品 | 決まりごと | 理由 |
| --- | --- | --- |
| 28BYJ-48 | 止めている間はコイルの電流を切る。指令が途絶えたときも同じ | 旧版と同じ（発熱・電池） |
| 28BYJ-48 | 刻みは Timer2 の割り込みで、`IO_STEP_TICK_US` ごとに位相を足す | I2C の読み取りや行の解釈でループが止まっても刻みが揺れない |
| MG996R | 指令が途絶えても**パルスを止めない**（その角度で保つ）。起動時は `PITCH_INITIAL_DEG` へ一気に動く | パルスを止めると脱力してカメラが倒れる。起動時の跳びはサーボの性質 |
| SRF02 | `Wire.setWireTimeout()` で I2C の時間切れを付け、時間切れは `st=1` で送る | I2C が固まって `loop` が止まるのを防ぐ（**使っている Arduino AVR コアがこの関数を持つかを `WP-IO-02` のビルドで確かめる**） |
| 全体 | AVR のウォッチドッグ（`IO_WDT_TIMEOUT`）。`loop` が回るたびに叩く | それでも固まったら再起動する。**再起動するとピッチが `PITCH_INITIAL_DEG` へ跳ぶ**（受け入れる。[-open.md](DetailedDesign-open.md) `P-8`） |

## 3. 電源

| 何を | どこから | 非常停止で | 備考 |
| --- | --- | --- | --- |
| 昇降部 | 旧版と同じ | 切れる（モータ）／未確認（ESP32。旧版 `D-3`） | |
| UnitV2 | モバイルバッテリの**出力 B**（USB Type-C） | 切れない | 5 V・500 mA |
| Arduino UNO | **出力 B**（UnitV2 と同じ側。USB-B または 5 V ピン） | 切れない | **サーボと分ける**（下記） |
| **MG996R・28BYJ-48（ULN2003）** | モバイルバッテリの**出力 A**（モータ専用） | 切れない | 大きめのコンデンサ（数百〜1000 µF）を近くに置く |
| SRF02 | UNO の 5 V | 切れない | 消費は小さい |

**モータの電源を UNO・UnitV2 と分ける**: MG996R は動き出しや拘束で大きな電流を流す。同じ出力だと電圧が落ちて **UNO が再起動し、ピッチが初期角へ跳ぶ**（§2.4）・UnitV2 が落ちる。
**出力が 2 つあり、モータ側の出力が MG996R の拘束電流をまかなえるモバイルバッテリ**を使う（[-open.md](DetailedDesign-open.md) `D-9`）。**GND はすべて共通にする。**
