# docs/plan/detailed — 詳細設計書

[完全設計書](../spec/README.md)（`docs/plan/spec/`）を入力とし、**実装できる形に落とした設計書。**

**本体は [DetailedDesign.md](DetailedDesign.md)。**
**2026-09-25 時点で骨格のみ。**完全設計書の構成の問い（[Spec-open.md](../spec/Spec-open.md) §2.2）が決まってから書く。

---

## 1. 位置づけ

| 文書 | 役割 |
| --- | --- |
| `docs/plan/spec/` | **完成形の正本。**確定した方針はここが正 |
| **`docs/plan/detailed/`（ここ）** | **詳細設計書。**ノード名・トピック名・ピン・ファイル構成・アルゴリズム・作業パケット |
| `docs/architecture.md` | **現状実装**の保守・拡張ガイド（as-built）。実装開始時に作る |

実装に入る前に `CLAUDE.md`「方針変更時のルール」に従い、**先に `docs/plan/spec/` を更新する。**
**完全設計書を詳細設計書に合わせて書き換えることはしない。**完全設計書が上流である。

### 1.1 完全設計書との境界

| 完全設計書に書くこと | 詳細設計書に書くこと |
| --- | --- |
| 「昇降機が上がっている間は走行させない」 | どの信号を誰が出し、th-system のどこで受けて速度を 0 にするか |
| 「通信が途絶えたら一定時間内に止まる」 | ウォッチドッグの時間・監視する周期・実装する場所 |
| 「上限・下限を越えて動かない」 | リミットスイッチのピン・論理・判定する関数 |

完全設計書の対応する章ができてから足す。

---

## 3. 実装者への 3 つの約束

th-system と同じ約束を置く。**詳細設計はこの 3 つを満たすように書く。**

| # | 約束 |
| --- | --- |
| **1** | **担当パケットの §2 に挙がった節だけ読めば実装できる。**完全設計書を読む必要はない |
| **2** | **名前を発明する必要がない。**必要な名前はすべて [-names.md](DetailedDesign-names.md) にある |
| **3** | **完了したかどうかを自分で判定できる。**受け入れ条件はすべて実行可能なコマンドになっている |

**この 3 つが崩れている箇所を見つけたら、実装を止めて設計書側を直す。**
黙って推測で埋めない（推測は次のセッションで別の推測になる）。

---

## 4. 完全設計書が更新されたとき

1. [-open.md](DetailedDesign-open.md) §2 の申し送り表を見直す（直った項目は行を消す）
2. 変更に対応する詳細設計の節と、影響する作業パケットの受け入れ条件を直す
3. **完全設計書を詳細設計書に合わせて書き換えることはしない**
