# Spec-open — 未確定事項・決定の記録・th-system との関係

[Spec.md](Spec.md) の詳細。**何が決まっていないか**はここが正。
決まったら §4 に 1 行記録し、該当する Spec ファイルへ反映してから §2 の行を消す。

ID の付け方: 本システムの未確定事項は `H-<分類><番号>`（th-system の `O-a1` 等と衝突させないため）。
分類は `G`（目標）・`S`（範囲）・`A`（構成）・`V`（値・測定）・`X`（安全）・`U`（画面）。
**領域ごとの Spec ファイルに書いた未確定事項は、そのファイルの「未確定」節が正**（[Spec-safety.md](Spec-safety.md) §3・[Spec-ui.md](Spec-ui.md) §3）。

## 1. th-system との関係

**2026-09-25 ユーザー決定: th-system とは独立させ、互いに干渉しない。通信はしない。**
仕様変更が互いに波及しないようにするため（[Spec.md](Spec.md) §4 `HD-1`）。
唯一の共有物は**無線 AP（`th-rpi-ap`）**で、これは通信網を借りるだけで th-system と信号はやり取りしない。

th-system 側の関連項目と、この決定による扱い:

| th-system の ID | 内容 | 本システム側の扱い | 出典 |
| --- | --- | --- | --- |
| `O-a1` | カメラ昇降が要求する位置決め許容差 | **答えるのは本システム**（`H-V2`）。独立させても、盤前にどこまで正確に止まってほしいかは伝える必要がある（文書で伝える。信号ではない） | th-system [Spec-open.md](../../../../th-system/docs/plan/spec/Spec-open.md) §5.1 |
| `O-a6` | 昇降・撮影側との正式インターフェース | **通信しない**（本書 §4）。th-system の「作業中」ボタンは試験員の手操作のまま残る。正式な信号に置き換えるかは th-system 側の判断 | th-system [Spec-onsite.md](../../../../th-system/docs/plan/spec/Spec-onsite.md) §7.2 |
| — | 昇降機が上がったまま機体が動くと、機構損傷・転倒に影響しうる | **走行禁止などの連動は設けない**（本書 §4）。th-system の作業中ボタンも昇降状態とは連動しない（OFF にすればジョグも移動も通る。th-system [Spec-modes.md](../../../../th-system/docs/plan/spec/Spec-modes.md) `SM-3.1.2-062`〜`-066`）。**既知のリスクとして残る** | th-system `th_system_mobility_design_detail.md` §4.4 |

## 2. 未確定事項

### 2.1 目標と範囲

| ID | 問い | これが決まると決まるもの |
| --- | --- | --- |
| **`H-G1`** | 本システムの目標（th-system の G1〜G5 に相当するもの）は何か。接触 0・意図しない挙動 0 を本システムにも課すか | すべての設計判断の優先順位 |
| `H-S2` | 撮影した画像・映像をどこまで扱うか（ライブ表示だけか、静止画の保存・一覧・盤との紐付けまでか） | 保存先・容量 |
| `H-S4` | ズームや照明は要るか | 部品の手配 |

### 2.2 構成

| ID | 問い | 選択肢の例（決めていない） |
| --- | --- | --- |
| **`H-A8`** | **AP を共有することで th-system の通信を圧迫しないか** | 映像は帯域を食う。th-system は同じ 2.4 GHz の AP で LiDAR のデータを PC へ送っており、無線の不調で過去に大きく苦労している（th-system `CLAUDE.md`「環境の癖」）。**「互いに干渉しない」を守るには映像の解像度・フレームレートの上限を決め、th-system と同時に動かして確かめる必要がある** |
| `H-A9` | 操作端末は何か（th-system と同じタブレット・PC を使うか、別端末か） | 同じ端末なら画面の切替、別端末なら持ち物が増える |
| `H-A6` | 試験方法 | ESP32 は `pio test` の native 環境で純関数を試験 ／ ラズパイ側はホストの pytest ／ 実機のみ |

### 2.3 値・測定（先方・機構側に聞くか、実測するもの）

| ID | 項目 | 出どころ |
| --- | --- | --- |
| **`H-V1`** | **盤上部の高さの範囲**（最も低い盤・最も高い盤） | 先方（th-system `O-a2`「盤面高さ」と同じ問い合わせで取れる） |
| **`H-V2`** | **盤前に止まる位置・向きの許容差** —— th-system の `O-a1` の答えになる。**ヨー・ピッチで向きを直せるぶん、th-system への要求は緩められるはず** | 撮影要件から逆算 |
| `H-V3` | 昇降のストローク・速度・全行程の所要時間 | 機構の仕様 ／ 実測 |
| `H-V4` | 昇降機を最も高くしたときの重心高さと、転倒しない傾き・加速度 | 実測 |
| `H-V5` | ヨー・ピッチの可動範囲と、必要な角度の細かさ | 機構 ／ 撮影要件 |
| **`H-V6`** | **映像の遅延**（撮ってから画面に出るまで） | 実測。**映像を見て止める操作では、遅延のぶんだけ行き過ぎる**（[operation-ideas.md](../operation-ideas.md)） |
| `H-V7` | カメラ部のモバイルバッテリで何時間動くか | 実測。1 日の運用（th-system `Spec.md` G5）に足りるか |

### 2.4 安全

| ID | 問い | 関係 |
| --- | --- | --- |
| `H-X4` | 通信断・電源断のとき昇降機はどうなるか（その場で保持・自重で下がる） | 昇降モータはパワーウィンドウモータ。**ウォームギアで自己保持する型が多いので、電源が切れてもその場で止まる見込み**。実機で確かめる |
| `H-X7` | 非常停止でカメラ部（ヨー・ピッチ）は止まらない（モバイルバッテリ給電のため）。それで足りるか | ヨー・ピッチは小さなモータで、挟み込みの危険は昇降より小さい |
| `H-X5` | ヨー・ピッチの可動域の制限（配線の巻き込み・機構への干渉） | ステッピングは原点が分からないと可動域を守れない |

## 3. 先行試作から分かっていること

先行試作はどちらも**動作確認用の単体試作**で、仕様の正ではない。詳細は [source/README.md](../source/README.md)。

| 分かっていること | 出典 |
| --- | --- |
| 昇降モータは ESP32 + Cytron MD10 系（DIR+PWM の 2 線制御）で上昇・下降・停止できる。**`elevator-motor-control` は昇降機の仮動作用プログラム**（2026-09-25 ユーザー） | `../elevator-motor-control/設計書.md` §2 |
| 通信断での自動停止（デッドマン 600 ms）と連続駆動の上限（暫定 10 s）で**リミットスイッチ無しを暫定的に補っている**。上下端での衝突はソフトだけでは防げず、人が見て操作する前提 | 同 §7 |
| ウォッチドッグを 600 ms にしたのは、th-system が 300 ms で WiFi ジッタによる誤停止を踏んで緩和した実績に倣ったもの | 同 §3 |
| `th-rpi-ap` に STA として乗る構成で動いている | 同 §3 |
| ESP32-CAM での無線カメラ試作（`esp32cam-test`）は**採用しない**。カメラ部はラズパイ 4 ＋ Web カメラになった（§4） | `../esp32cam-test/` |
