# Spec-open — th-system からの要求・未確定事項・決定の記録

[Spec.md](Spec.md) の詳細。**何が決まっていないか**はここが正。
決まったら §4 に 1 行記録し、該当する Spec ファイルへ反映してから §2 の行を消す。

ID の付け方: 本システムの未確定事項は `H-<分類><番号>`（th-system の `O-a1` 等と衝突させないため）。
分類は `G`（目標）・`S`（範囲）・`A`（構成）・`V`（値・測定）・`X`（安全）。

## 2. 未確定事項

### 2.1 目標と範囲

| ID | 問い | これが決まると決まるもの |
| --- | --- | --- |
| **`H-G1`** | 本システムの目標（th-system の G1〜G5 に相当するもの）は何か。th-system の G1（接触 0・意図しない挙動 0）を本システムにも課すか | すべての設計判断の優先順位 |
| **`H-S1`** | **操作はどこからするか。**th-system の WebUI に統合するか（th-system SD-1「操作系は WebUI のみ」）、別画面か | 画面の担当・非常停止の一元化・操作者が 1 人で完結できるか |
| `H-S2` | 撮影した画像・映像をどこまで扱うか（ライブ表示だけか、保存・一覧・盤との紐付けまでか） | 保存先・容量・盤 ID の受け取りが要るか |
| `H-S3` | 盤前の低速並進を本システムが担当するか（th-system は保留） | 本システムが走行指令を出す必要があるか |
| `H-S4` | カメラの自由度は高さ・ピッチ・ヨーの 3 つで確定か。ズームや照明は要るか | 機構・部品の手配 |

### 2.2 構成

| ID | 問い | 選択肢の例（決めていない） |
| --- | --- | --- |
| **`H-A1`** | **th-system との結合の深さ** | th-system と状態・通信網を共有する一部として動く ／ 独立した機器として必要な信号だけやり取りする（どちらを採るかで §1 の結合の章の書き方が変わるので spec で決める。**具体的な手段（ROS2・WebSocket 等）は詳細設計**） |
| **`H-A2`** | **昇降モータを誰が駆動するか** | 昇降専用の ESP32（先行試作 `elevator-motor-control` の形） ／ th-system の走行用 ESP32 に相乗り |
| `H-A3` | カメラの映像をどこへ送るか | 無線（先行試作 `esp32cam-test` の形・th-system の AP に乗る） ／ 有線でラズパイか PC へ |
| `H-A4` | ピッチ・ヨーの駆動方式 | サーボ ／ ステッピング ／ 固定（高さだけ動かす） |
| `H-A5` | 先行試作 2 つ（`../elevator-motor-control`・`../esp32cam-test`）をこのリポジトリへ取り込むか、参照に留めるか | — |
| `H-A6` | ファームウェアの試験方法 | `pio test` の native 環境で純関数を試験 ／ 実機のみ |

### 2.3 値・測定（先方・機構側に聞くか、実測するもの）

| ID | 項目 | 出どころ |
| --- | --- | --- |
| **`H-V1`** | **盤上部の高さの範囲**（最も低い盤・最も高い盤） | 先方（th-system `O-a2`「盤面高さ」と同じ問い合わせで取れる） |
| **`H-V2`** | **撮影に要る位置・向きの許容差** —— これが th-system の `O-a1` の答えになる | 撮影要件から逆算 |
| `H-V3` | 昇降のストローク・速度・全行程の所要時間 | 機構の仕様 ／ 実測 |
| `H-V4` | 昇降機を最も高くしたときの重心高さと、転倒しない傾き・加速度 | 実測 |

### 2.4 安全

| ID | 問い | 関係 |
| --- | --- | --- |
| **`H-X1`** | **昇降機が上がっている間、機体の走行を禁止するか・減速で許すか。**誰がそれを止めるか（本システムが走行を止める信号を出すのか、th-system が昇降状態を見て自分で止めるのか） | **現行の作業中ボタンでは塞げない**（§1。OFF にすればジョグも移動も通る）。th-system `O-a6` |
| **`H-X2`** | 上限・下限の検知手段（リミットスイッチ・エンコーダ） | 先行試作には無く、**ソフトだけでは上下端での衝突を防げない**（§3） |
| `H-X3` | th-system の非常停止（物理・画面）で昇降も止めるか。逆に、昇降側の異常で走行を止めるか | 非常停止の一元化 |
| `H-X4` | 通信断・電源断のとき昇降機はどうなるか（その場で保持・自重で下がる） | 機構の選定 |

## 3. 先行試作から分かっていること

先行試作はどちらも**動作確認用の単体試作**で、仕様の正ではない。詳細は [source/README.md](../source/README.md)。

| 分かっていること | 出典 |
| --- | --- |
| 昇降モータは ESP32 + Cytron MD10CR3（DIR+PWM の 2 線制御）で上昇・下降・停止できる構成で試作済み | `../elevator-motor-control/設計書.md` §2 |
| 通信断での自動停止（デッドマン 600 ms）と連続駆動の上限（暫定 10 s）で**リミットスイッチ無しを暫定的に補っている**。上下端での衝突はソフトだけでは防げず、人が見て操作する前提 | 同 §7 |
| ウォッチドッグを 600 ms にしたのは、th-system が 300 ms で WiFi ジッタによる誤停止を踏んで緩和した実績に倣ったもの | 同 §3 |
| 無線カメラは Freenove ESP32-WROVER CAM（OV2640）で MJPEG 配信を試作済み | `../esp32cam-test/src/main.cpp` |
| th-system の AP（ラズパイ・2.4 GHz）に STA として乗る構成で試している | 両試作 |
