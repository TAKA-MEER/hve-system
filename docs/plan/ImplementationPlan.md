### 2.1 実装エージェントの動かし方（優先順・herdr ／ orca）

**1 作業パケット ＝ 1 ブリーフ ＝ 1 エージェント**。並行数は作業の独立性で決める。

**実装エージェントの優先順**（2026-11-18 ユーザー決定。上が使えない〈枠が尽きた・起動しない・提供終了〉ときだけ次へ移る）:

| 順 | エージェント | 投げ方 | 備考 |
| --- | --- | --- | --- |
| 1 | **codex** | orca／herdr の端末で起動（`orca worktree create … --agent codex`）。手順は下の opencode と同じ | hve-system では未使用。許可プロンプトの答え方などは使ってから書き足す |
| 2 | **DeepAI**（DeepAI Code の無料モデル） | `deepai-code-dispatch` スキル（MCP `deepai-code`）。worktree は `~/.deepai-code/worktrees/` にでき、`.briefs/`・`.venv*` は無い | ブリーフはメッセージで渡すか worktree に置く。リポジトリに `AGENTS.md` は無いので、守ることはブリーフに書く |
| 3 | **opencode** | 下の手順 | 無料枠がすぐ尽きる（CLAUDE.md「環境の癖」） |
| 4 | **Sonnet のサブエージェント** | Claude Code の Agent ツール（`isolation: "worktree"`） | これまで opencode が尽きたときの引き継ぎに使ってきた |

どれでも、ブリーフ・受け入れ検査（§2.2）・git の持ち方（§2.3）は同じ。

**どちらの中で動いているかは環境変数で見分ける**（2026-10-01。th-system で herdr から orca への乗り換えを検討中で、両方を使う。orca の試用結果は th-system 側の記録を移した）。

```bash
env | grep -E '^(TERM_PROGRAM|ORCA_TERMINAL_HANDLE|HERDR_PANE_ID|HERDR_ENV)='
```

| 見えるもの | いる場所 | 使う手順 |
| --- | --- | --- |
| `TERM_PROGRAM=Orca` ／ `ORCA_TERMINAL_HANDLE=term_…` | **orca** | 下の「orca の場合」 |
| `HERDR_PANE_ID` ／ `HERDR_ENV` | **herdr** | 下の「herdr の場合」。※変数名は th-system が herdr 0.8.2 の実行ファイルから拾ったもので、ペイン内での実在は未確認 |
| どちらも無い | 素の端末 | どちらかのコマンド（`orca status` ／ `herdr status`）が通る方を使う |

#### herdr の場合

```bash
herdr tab list                                    # ImplementAgent タブの tab_id を確認
herdr pane split --pane <既存pane> --direction right   # 体を増やすときはペインを分ける
herdr agent list                                  # pane が agent="opencode" として自動検出されたか確認
herdr agent rename <pane_id> <name>               # 名前を付ける（start ではなく rename）
herdr agent prompt <name> "指示書は .briefs/brief-<ID>.md。全文を読み前提誤りを指摘、無ければ最後まで実装"
herdr agent get <name>                            # agent_status を 10 秒間隔でポーリングして監視
```

| 項目 | 決まりごと | 理由 |
| --- | --- | --- |
| ブリーフの置き場 | **`.briefs/`（リポジトリ内・gitignore 済み）** | リポジトリ外に置くと opencode が「外部ディレクトリアクセス許可」で毎ターン止まる |
| 一時ファイル | **`.briefs/tmp/`。`/tmp` を使わせない** | 同上。「Allow always」を選んでもターンを跨いで再発する |
| 既に opencode が動いているペイン | **`agent start` を打たない。`agent rename` だけ**で登録する | `start` はシェルプロンプト待ちを期待するため、動作中のセッションに文字列を打ち込んで壊す |
| 並行させるとき | **片方を `git worktree` に隔離する** | 同じファイルを 2 体が触ると衝突する。`herdr worktree` が helper を持つ |
| 監視 | `herdr agent get` のポーリング | `herdr agent wait --until` は状態の遷移を取りこぼす |
| 承認プロンプト | `herdr agent send-keys <name> Left Left Right Enter` で「Allow always」 | カーソル位置が読めないので左端へ寄せてから 1 つ右 |
| コミット | **細かく切らせる** | **無料枠・クォータで途中で止まる前提。**opencode は上限に達すると idle のまま進まなくなる |
| `git push` | **投げない。実装管理担当が検証してから押す** | — |

#### orca の場合（th-system が 2026-10-01 に試用。hve-system では 2026-10-07 の `WP-BASE-02` から使っている）

```bash
orca worktree create --name <n> --no-parent --setup skip --base-branch <元のブランチ> --agent opencode --json   # worktree 作成と opencode 起動を 1 回で（元のブランチは main）
git -C <worktreeのpath> branch -m yisahia787/<n> <種別>/<主題>   # orca はブランチ名を yisahia787/<n> にするので付け替える（2026-11-10 から。以前は <n>）
mkdir -p <worktreeのpath>/.briefs/tmp                    # .briefs は gitignore なので新しい worktree には無い。ブリーフもここに置く
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000 --json   # satisfied:true を確かめてから送る
orca terminal send --terminal <handle> --text "指示書は .briefs/brief-<ID>.md。…" --enter --json
orca terminal read --terminal <handle> --limit 60        # 監視。画面に `esc interrupt` があれば作業中
orca worktree rm --worktree path:<path> --force --json   # 片付け。フォルダ・ターミナル・ローカルブランチまで消える（hve-system では `id:<repoId>::<path>` は黙って何もしなかった。2026-10-07）
```

| 項目 | 決まりごと | 理由 |
| --- | --- | --- |
| `worktree create` | **`--setup skip` を必ず付ける** | th-system では repo 設定のセットアップ hook が `pnpm install`（既定）で失敗した。hve-system でも直下に `package.json` は無い |
| worktree の置き場 | `~/orca/workspaces/hve-system/<n>`（リポジトリの外） | `.venv/` も無いので、カメラ部の試験は worktree 内で作り直す |
| 投入の確認 | `terminal send` の結果ではなく**画面を読んで**確かめる | opencode は `provider: unsupported` で、ターンが始まったことを orca が証明できない |
| 監視 | `terminal read` を 30 秒間隔で読むスクリプトを Monitor で回す（`esc interrupt` が 2 回続けて無ければ停止） | ターン終了の通知が無い |
| 承認プロンプト | **未確認**。`terminal send` に矢印キーを送るオプションが無い | th-system の試用では 1 度も出なかった。出たら確かめてここを書き換える |

ブリーフ・一時ファイル・コミット・`git push` の決まりごとは herdr の表と同じ。

**ブリーフに必ず書くこと**: 作業ブランチ名／読むべき設計書の節（担当パケットの §2）／
受け入れ条件（実行できるコマンド）／触ってよいファイルの範囲／**触ってはいけないもの（th-system のリポジトリ）**。

### 2.2 受け入れ検査（実装管理担当がやること）

**実装は信用してよい。テストは絶対に信用しない。**（th-system で、通るだけで何も検出しないテストが繰り返し出てきた）

1. テストを**自分で回す**（ホストの pytest ／ `pio test` ／ 画面の試験。何を使うかは構成が決まってから §5 に書く）
2. **変異チェックを 1〜2 件は自分で再実行する** — 実装ファイルを `sed` で壊し、該当テストが赤くなるか。
   **停止・ウォッチドッグ・上下限の判定は、純関数だけでなく呼び出し側を壊す変異も入れる**
3. `git show <commit>` で差分がブリーフの範囲内かを目視する
4. 実機が要るものは、書き込みと起動スモークまで自分で

### 2.3 git の運用（実装管理担当が持つ）

**ブランチ・マージ・push・掃除はすべて実装管理担当の責任。**
実装エージェントは**自分の作業ブランチにコミットするところまで**で、それ以外の git 操作はしない。

| 操作 | 誰が | 備考 |
| --- | --- | --- |
| ブランチを切る | **実装管理担当** | ブリーフを渡す前に切り、エージェントにはブランチ名を伝える |
| コミットする | 実装エージェント | **細かく切らせる**（§2.1） |
| `main` へマージ | **実装管理担当** | §2.2 の受け入れ検査を通してから |
| `git push` | **実装管理担当** | エージェントには投げさせない |
| ブランチの掃除 | **実装管理担当** | 下記「掃除」 |

#### ブランチ

- 命名は **`<種別>/<主題>`**。種別は `feat` / `fix` / `docs` / `tune` / `chore` / `test`。
  作業パケット単位なら記号を入れる（例: `feat/wp-lift-01-watchdog`）。
- **1 作業パケット ＝ 1 ブランチ。**複数のパケットを 1 本に混ぜない
  （混ぜると片方だけ差し戻せない。`git add -p` が使えない環境なので後から分割もできない）。
- **文書だけの修正は `main` へ直接コミットしてよい。**コードを含むものは必ずブランチを切る。

#### マージ

- **`--no-ff` でマージする。**作業の単位が履歴に残る。
- **squash しない。**台帳や設計文書がコミットハッシュを名指しで参照するため、潰すと追跡が切れる。
- マージコミットの本文に**検証の結果を数字で書く**（例: ホスト pytest 120 passed、変異 2 件で赤を確認）。

#### 計画書を都度更新する

**この計画書は、証拠が動いたその作業の区切りで更新する。まとめて後で直さない。**
（th-system で 14 回マージして計画書に反映されたのが 1 行だけになり、完了済みの項目を「次にやること」と答えかけた）

| いつ | 何を直すか |
| --- | --- |
| `main` へマージした直後 | §4 の状態列、§6 の該当行（済みなら取り消し線＋コミット）、§3 |
| 実機確認を記録したとき | 同上。証拠の水準（§1）を「配線済み」→「実機確認済み」へ上げる |
| 台帳（`EXCEPTION-LEDGER.md`）の状態を変えたとき | 台帳 ID を併記している §4・§6 の行 |

- 文書だけの更新なので `main` へ直接コミットしてよい。マージと同じ区切りで、**別コミット**にする。
- 直したら §1 の「最終同期」の日付を更新する。
- **§6 から次の作業を選ぶ前に**、`git log --merges --since=<最終同期日> main` と突き合わせる。

#### コミットメッセージ

`<種別>(<範囲>): <日本語の 1 行>` ＋ 本文に**何をなぜ**（どう直したかは差分を見れば分かる）。
末尾の帰属行は会話の指示に従う。

#### 掃除

- **マージしたブランチはその場で消す**（ローカル・`origin` とも）。溜めない。
- 放置されたブランチは四半期ごとに棚卸しする。消したブランチの SHA はコミットメッセージに残す。

#### `CLAUDE.md` と重複させない

作業前の `git status` 確認、自分が変更したファイルだけをステージする、`git add -A` を使わない、
`git add -p` が使えないので 1 ファイルに複数の関心事を混ぜない ── これらは
`CLAUDE.md`「作業開始前のルール」が正。ここには書かない。

### いま分かっている危険

- **天井の判定は無線を挟み、v2 では命令の出どころ（接続）で使うかが変わる。**`WP-LIFT-03`・`WP-CAM-04` の変異チェックを**管理担当が必ず自分で**やる
- **上端の検知が無い**（`W-1`）。昇降部の画面から上昇させると、自動で止まるのは連続駆動の上限だけ。実機で上昇を試すときは人が見ながら短く
- **UNO の TX は 5 V、UnitV2 の UART は 3.3 V。**UNO → UnitV2 には分圧が要る（2026-10-07 に実測。[DetailedDesign-hardware.md](detailed/DetailedDesign-hardware.md) §2.3）。**D0 に線が付いていると UNO に書き込めない**
- UnitV2 の CPU・メモリで 1080p の取り込みが回るか分からない（`WP-MEAS-06`）
- 映像が th-system の無線を圧迫しうる（`WP-MEAS-03` まで分からない）
