# docs/plan — 設計文書と検討中の方針メモ

まだ確定していない方針・比較検討・たたき台を置く場所。

**ただし `spec/` と `detailed/` はここの例外で、確定済みの正本である。**
`spec/` = 完成形（何が・どう振る舞うべきか）、`detailed/` = 詳細設計（どう実装するか）。
**この 2 つ以外**の内容は検討メモであり、`spec/` を上書きしない。
ここで結論が出た時点で、CLAUDE.md「方針変更時のルール」に従い先に `spec/` を更新する。

## 運用ルール: 本体は一目で読める分量に保ち、詳細は別ファイルに分ける

検討が進むと本体ドキュメントは必ず肥大化する。読み返す人（と AI）が全体像を
掴めなくなるのを防ぐため、以下の構成を守る。

### 本体（`<テーマ>.md`）に置くもの

* **結論**（数行）
* **比較表**（判断に使う軸と数値。表そのものが要約になっているもの）
* **次にやること**のリスト
* 詳細ファイルへのリンク一覧

**根拠・計算・各案の詳細な長所短所・却下理由は本体に書かない。**
「一目で読める」＝スクロールせずに何が結論かが分かる状態を維持する。

### 詳細ファイル（`<テーマ>-<側面>.md`）に置くもの

テーマ名を接頭辞にして分割する。1 ファイル 1 側面。

| 側面 | 典型的な中身 |
| --- | --- |
| `-premises` | 前提・制約・実測値・測定が必要な項目・評価軸 |
| `-options` | 候補の詳細と比較 |
| `-recommendation` | 推奨・意思決定・関係者に確認する項目 |
| `-ideas` | 定石から外れた案・アイデア置き場 |

例: 昇降機構の方式を検討するなら `lift.md` ＋ `lift-premises.md` / `lift-options.md` /
`lift-recommendation.md`。結論が出たら spec へ移す。

### 相互参照の書き方

* **同じファイル内**の節は `§0.1` のようにそのまま書く。
* **別ファイル**の節は Markdown リンクにする — `[§0.1](lift-premises.md)`。
  番号だけ書くとどのファイルの節か分からなくなる。
* `docs/plan/spec/` / `docs/architecture.md` の節を指すときは
  **必ずファイル名を付ける**（`Spec-lift.md §4.2`）。plan 側の節番号と衝突するため。
* **th-system の文書を指すときは「th-system」を付ける**（th-system `Spec-onsite.md` §7.1）。
  ファイル名が同じ（`Spec.md` 等）で、どちらのリポジトリか分からなくなるため。
  リンクは**そのファイル自身の位置からの**相対パスで書く（`docs/plan/` 直下なら `../../../th-system/...`、`docs/plan/spec/` なら `../../../../th-system/...`）。

### 分割のタイミング

* 本体が **200 行を超えたら**分割を検討する。
* 1 つの節が **本体の他の節より明らかに長くなったら**、その節を切り出す。
* 分割時は**文章を書き換えず、そのまま移す**。参照の書式だけ直す。
  移動と加筆を同時にやると、どこが変わったのか diff から追えなくなる。
